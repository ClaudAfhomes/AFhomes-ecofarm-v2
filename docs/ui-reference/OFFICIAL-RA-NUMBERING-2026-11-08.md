## A. Existing implementation and verified inventory

- `customers.ra_number`: company Customer ID, generated by `private.assign_company_customer_id()` using `private.company_customer_id_counters`. It resembles `YYYY-NNNN` but is **not** the official RA number. Existing company IDs can exceed four serial digits and include older imported formats; this task does not change them.
- `customers.customer_number` (`AF-CUS`) and `customer_code` (`AF-CC`) are additional existing customer identifiers. UUID ownership and all values are preserved.
- Canonical RA storage is `reservation_agreements.reservation_number`, already unique/indexed. Application-origin creation used `private.claim_af_id('AF-RES',...)`; the legacy sale-origin save used a separate `RES-...` expression.
- Application approval already creates/submits/executes a reservation through authorized idempotent RPCs. The new allocator retains these events and authorization. A draft Customer Application does not issue an RA number.
- `public.generate_vip_card_number(text,text,integer)` used an independent `private.vip_card_number_seq`. A normal customer PATCH could invoke it before activation; historical imports could also mint an ID without its proper activation context.
- Previously issued VIP IDs live in `customers.vip_card_number`, protected by a unique index and permanent `private.vip_card_number_issuances` registry. Existing Standard and historical Non-Standard IDs are immutable.
- Current schema supports only **one membership per customer** (`memberships.customer_id` unique). This task does not remove that business constraint or reassign customer identities to simulate more memberships. Enabling multiple memberships would require a separate membership/storage workflow decision.

Read-only live aggregate/catalog inspection of project `ikaevepedpqygdlipsei`: two reservations, both historical `AF-RES`; zero annual official RAs; zero annual/overlength RA references in durable aliases/audit history; two company Customer IDs, two issued VIP IDs and two memberships. There was no observed annual RA high-water conflict. Migration history has 131 entries, ending at `20261229000001`. Generator bodies confirmed the separate customer counter, old random RA allocator and independent VIP sequence. No customer names or credentials were exported.

## B. Changes and behavior

New additive migration: `supabase/migrations/20261230000001_afhomes_official_ra_numbering.sql`.

SHA-256: `e589238c9fcf75dcf1b004a95d682a458038729713ae30c660ce434c0979a064`.

- Independent private year counters and immutable issuance ledger; the ledger has no reservation FK, so deletion/cancellation cannot release a number. Year/sequence and full number are unique; reservation UUID is unique in the ledger. New issue timestamps are captured at issuance in Asia/Manila. Historical issuance timestamps remain unknown (NULL), explicitly marked historical rather than fabricated.
- One-time migration inventory includes existing numeric RAs plus durable aliases and reservation-number audit references. It seeds high-water marks without renumbering records. Invalid/overlength/whitespace annual references, zero serial/year or conflicting ownership fail migration validation; the transaction rolls back. Normal allocation never uses MAX.
- Allocation locks only the applicable year's counter row, starts at 0001 and rejects after 9999. Replays retain the same number and original issue year. A reservation INSERT trigger covers both existing creation paths; number edits are rejected. Superseded random/default generation is removed from the two issuance callers.
- The actual trigger-assigned number is read back into the creation RPC for its audit/evidence. UUID relationships and idempotent approval/creation behavior are retained.
- VIP issuance is called from the existing activation function after its unchanged permission and Finance-verified full-payment checks. It requires the executed contract, and application-origin purchases must also be finalized. It uses the RA's four-digit sequence padded to five digits and the **same activation timestamp** written by activation. Tier and payment encoding reuse the established Standard-only policy (Spot Cash/Move A: C01; configured installment terms: T plus two-digit months). No independent VIP counter is used.
- Existing VIP IDs are returned unchanged. Candidate collisions with live or permanently issued IDs reject activation with `VIP_RA_NUMBER_COLLISION`; there is no retry using another sequence, and the transaction rolls back membership/customer changes.
- Customer edits no longer mint VIP IDs. The old context-free generator is disabled for service callers. Prospective imports without a final VIP ID defer issuance; historical activated imports must supply their evidence-backed existing ID. Supplied Standard/Non-Standard historical IDs remain supported.
- Customer ID labels no longer call that value an RA number. Draft review has a read-only pending official-number state; older proposed draft references remain separately labelled legacy information. They are never printed as official numbers. Issued reservation views, Finance, documents and API responses retain canonical `reservation_number` values.
- Complete annual RA searches and historical `AF-RES-XXXXX` searches use exact equality on the existing unique index. Partial search, filters, permissions and pagination remain.
- Payment reports/exports have a separate Official Reservation Agreement Number column; pre-sale RA values are no longer placed under Sale number. UUID payment linkage, balances and verification remain unchanged.
- Membership/card/portal DTOs now expose VIP Card ID separately from the membership code, using existing customer joins. Printed staff cards and membership/customer screens label both identifiers distinctly. QR credentials and membership codes are unchanged.

## C. Performance

- Reuses `reservation_agreements_reservation_number_key` for exact lookups; no redundant public search index.
- New counter year PK and issuance PK/unique reservation UUID/year-sequence indexes support bounded indexed operations. No global advisory lock is added; only same-year RA issuance serializes. VIP issuance adds a bounded existing sale/customer lookup once per activation, not per list row.
- VIP display extends existing joins; no N+1 lookup path is added.
- The one-time migration scans reservation, alias and audit history to preserve consumed numbers. A large audit history can make that step expensive; rehearse against a protected copy and measure the authorized rollout window. No permanent audit index was added solely for this one-time operation.

## E. Rollout prerequisites and unresolved legacy cases

No production/shared apply is authorized. Review the exact migration and hash, rehearse on a protected populated copy, and re-audit current target history and all numeric/retired RA references before any separately approved apply. Deploy the corresponding API/UI changes together with an approved migration plan. Preserve backups and all issuance ledgers; rollback is a forward repair, never a counter reset or renumbering.

The approved VIP format omits the RA issuance year. Equal sequences from different RA years can collide on the same activation day with the same tier/payment encoding. This is proven and **fails closed**. Changing that outcome needs an approved format/policy revision; none was invented.

Historical `AF-RES` reservations with no already-issued VIP ID have no numeric sequence derivable under the approved formula. New VIP issuance for those rows is blocked with `VIP_OFFICIAL_RA_SEQUENCE_REQUIRED`. Resolution needs an explicit grandfathering/mapping policy or an evidence-backed previously issued historical ID. No Customer ID is substituted and no old RA is renumbered.

The existing one-membership-per-customer restriction remains. It preserves customer identity, but broader multi-membership support is outside this numbering patch and needs a separate schema/lifecycle decision.
